# 1. 目的

本標準は、ポータルを構成するすべてのサブシステムで共通となるモジュール構成・責務・依存関係を定義する。

システムの保守性・拡張性・再利用性を向上させるため、すべてのアプリケーションは本標準に従って設計・実装する。

---

# 2. 基本方針

ポータルでは以下の設計方針を採用する。

- モジュール単位で開発する。
    
- 責務を明確に分離する。
    
- 業務ロジックはServiceへ集約する。
    
- データアクセスはRepositoryへ集約する。
    
- UIは表示・入力のみを担当する。
    
- システム間は疎結合を維持する。
    
- 将来の機能追加・AI導入に対応できる構造とする。
    

---

# 3. モジュール構成

すべてのサブシステムは以下の構成を基本とする。

```text
modules/

└── module-name/

      module.handler.ts
      module.service.ts
      module.repo.ts
      module.types.ts
      module.validator.ts
```

必要に応じて以下を追加する。

```text
module.dto.ts

module.mapper.ts

module.constants.ts

module.utils.ts
```

# 4. レイヤー構成

ポータルでは以下のレイヤー構成を採用する。

**FIG-001 モジュールアーキテクチャ**

```text
React UI

      │

      ▼

Electron IPC

      │

      ▼

Handler

      │

      ▼

Service

      │

      ▼

Repository

      │

      ▼

Database
```

すべての処理は上位レイヤーから下位レイヤーへ流れる。

---

# 5. 各レイヤーの責務

## UI

- 画面表示
    
- ユーザー入力
    
- 状態表示
    

業務ロジックは実装しない。

---

## IPC

- RendererとMainの通信
    

通信処理のみを担当する。

---

## Handler

- IPC受付
    
- 入力値チェック
    
- Service呼び出し
    

業務ロジックを持たない。

---

## Service

- 業務ロジック
    
- システム間連携
    
- 判断処理
    
- トランザクション制御
    

ポータルの中心となるレイヤーとする。

---

## Repository

- CRUD
    
- SQL実行
    
- DBアクセス
    

業務ロジックは実装しない。

---

## Database

- データ永続化
    

データ保存のみ担当する。

---

# 6. 依存関係

```text
UI

↓

Service

```

逆方向の依存は禁止する。

# 8. Service層

Service層はポータル標準として必須とする。

Serviceでは以下を担当する。

- 業務ロジック
    
- Repository呼び出し
    
- 他モジュール連携
    
- 判断エンジン呼び出し
    
- 更新処理
    
- トランザクション制御
    

複数Repositoryを組み合わせる処理は必ずServiceへ実装する。

---

# 9. 判断エンジン

加工判断など複雑な処理はServiceから判断エンジンを呼び出す。

**FIG-002 判断処理構成**

```text
Handler

↓

Service

↓

Judgement Engine

↓

Repository
```

判断ロジックはRepositoryへ実装しない。

---

# 10. モジュール独立性

各モジュールは独立して開発・保守できる構成とする。

モジュール間の直接依存は禁止し、必要な場合はServiceを介して連携する。

---

# 11. 共通処理

複数モジュールで利用する処理は `shared` ディレクトリへ配置する。

例

```text
shared/

├── logger

├── errors

├── validation

├── ipc

├── database

└── utils
```

共通処理を各モジュールへ重複実装しない。

---

# 12. 将来拡張

本構成は将来以下の追加を想定する。

- AIサービス
    
- 判断エンジン
    
- 外部API
    
- 帳票生成
    
- バッチ処理
    
- 通知機能
    

新しい機能は既存レイヤーへ影響を与えない形で追加できる構造とする。

---

# 13. 設計原則

本標準では、

**「一つのレイヤーは一つの責務だけを持つ」**

ことを基本原則とする。

また、

- UIは表示に専念する。
    
- Handlerは受付に専念する。
    
- Serviceは業務に専念する。
    
- Repositoryはデータアクセスに専念する。
    

という責務分離を徹底する。

本標準は、ポータルを構成するすべてのサブシステムに適用し、長期的な保守性・拡張性・品質の維持を実現する。
